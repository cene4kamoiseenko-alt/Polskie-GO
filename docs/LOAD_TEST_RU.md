# Нагрузочный тест: 500 одновременных игроков

Прогон 2026-11-07. Скрипт — `scripts/load-test.ts` (`npm run load:test`). Подробности и ограничения ниже: прочитайте раздел «Что это значит и чего тест не показывает» до того, как делать выводы.

## Что именно проверялось

500 виртуальных «телефонов» против **настоящего Worker** (workerd через `wrangler dev --local`, тот же `wrangler.jsonc`, миграции 0001–0015, боевой seed: 147 уроков, 1 755 заданий) с локальной D1. Каждый игрок — со своим IP, подписанным `initData` (как из Telegram) и паузами «подумать»:

1. вход → знакомство → открытие приложения (8 запросов параллельно: профиль, маршрут, задания, магазин, домик, миссии, достижения, кошелёк);
2. миссия «Żabka» целиком (15 шагов, ответы верные);
3. урок целиком (все задания верно, не быстрее секунды на задание — антибот сервера), затем завершение;
4. цель дня → домашний бонус;
5. повторное открытие главной.

Все 500 в игре одновременно (разгон 5 секунд, в пике 500). Каждый 5-й игрок делает двойной ответ на шаг миссии, каждый 4-й — двойное завершение урока, каждый 3-й — двойное нажатие «забрать бонус»: **гонки проверены на самих параллельных запросах**.

## Что нашёл тест и что исправлено

1. **Двойное нажатие «Забрать бонус» показывало «+N Złotki» дважды.** Деньги начислялись один раз (ключ идемпотентности), но проигравший гонку запрос тоже получал `200 {granted: N}`: игрок на телефоне увидел бы два тоста. Теперь `atomic()` возвращает результаты пакета D1, а `claimHouseBonus` смотрит, изменила ли его операция баланс; опоздавший получает тот же отказ `already_claimed`, что и при обычном повторе. Тест — `housing.test.ts` («параллельные запросы»: ровно один 200 и один 400).
2. Двойной финиш урока возвращает сохранённый итог (так задумано: идемпотентный повтор, `finishResult` в сессии); награда одна — проверено сверкой баланса и журнала.
3. Остальное — без замечаний: 100 двойных ответов на шаг миссии засчитаны по одному, 125 двойных завершений урока — по одной награде.

## Что это значит и чего тест не показывает

**Показывает:** логика выдерживает 500 одновременных игроков без ошибок, потерянных и задвоенных наград, а ограничители не мешают обычному игроку. Серверный журнал ошибок и учёт Złotki остаются согласованными под параллельной записью.

**Не показывает (честно):**
- **Задержки — не прогноз для production.** Генератор нагрузки и Worker делят одну машину с 4 ядрами; `wrangler dev` добавляет свой слой (пустой статический файл отвечает за ≈ 5 мс, `/api/health` — за ≈ 9 мс); Worker локально — одна нить, а на Cloudflare запросы разносятся по множеству копий. Потолок на этой машине — около 140 запросов в секунду, поэтому «лавина» (500 входов за 5 секунд ≈ 5 000 запросов) выстроилась в очередь (вход в среднем ждал 15 секунд). Живая нагрузка размазана во времени.
- **Настоящая D1** (запись — по очереди в одной базе, чтение — через сеть) и **сеть Cloudflare** не участвовали: локальный SQLite быстрее.
- **Не телефоны:** Telegram WebView, iOS/Android, медленная сеть, сворачивание приложения, звук из R2 (MP3), оплата Stars, бот (webhook и cron-напоминания) в этом тесте не участвовали.
- Один сценарий (миссия + урок + бонус); экзамены, дуэли друзей, лидерборд под нагрузкой не гонялись.

**Риск, который стоит проверить на staging: лимит процессорного времени.** На бесплатном плане Cloudflare Workers — **10 мс CPU на запрос** (платный план — 30 с). Время обслуживания на свободном сервере (один игрок, запросы по очереди; `LOAD_MODE=probe`): `/api/journey` ≈ 22 мс, `/api/achievements` ≈ 15, `/api/shop` ≈ 14, `/api/house`, `/api/quests`, `/api/me` ≈ 10 мс; из них около 5 мс — пол самого `wrangler dev`, а часть — локальный SQLite, который на Cloudflare в CPU Worker не входит. Какая доля — CPU, отсюда не видно. **Если проект на бесплатном плане и `/api/journey` на staging упрётся в «Worker exceeded CPU time limit» (ошибка 1102), нужен платный план Workers ($5 в месяц) или облегчение этих запросов.** Это решение владельца; без измерения на staging я его не принимаю.

## Как повторить

```bash
npm run build                                   # нужны dist-cf и apps/server/seed.sql
npm run load:test                               # 500 игроков, ≈ 3 минуты, локальный Worker
LOAD_USERS=200 LOAD_RAMP_MS=2000 npm run load:test
LOAD_MODE=probe npm run load:test               # время обслуживания каждого эндпоинта без очереди
```

Против **staging** (`docs/STAGING.md`, раздел 5; production не трогать — тест создаёт N настоящих аккаунтов и выдаёт им награды):

```bash
LOAD_BASE_URL=https://polskie-go-staging.<аккаунт>.workers.dev LOAD_BOT_TOKEN=<токен тестового бота> LOAD_ALLOW_REMOTE=yes npm run load:test
```

На удалённой цели сверка базы пропускается (к D1 нет доступа) — считаются ответы и задержки; это и есть измерение, которого не хватает здесь. Начать стоит с `LOAD_USERS=50`, затем 200 и 500; в панели Cloudflare (Workers → Metrics) смотреть CPU time и ошибки 1102, в админке — «Ошибки за 24 часа».

Скрипт завершает `workerd` по имени (`pkill -f workerd`): иначе после прогона остаётся процесс на порту и отвечает следующему запуску с чужой базой (так проявилась ошибка самого скрипта при отладке — к приложению она не относится).
