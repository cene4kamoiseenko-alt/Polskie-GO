## 2. Что сделать вам (один раз; из среды разработки этого не сделать)

1. **Двухфакторная защита** на аккаунтах Cloudflare, GitHub и Telegram (аккаунт, которому принадлежит бот). Проверьте, у кого есть доступ к Cloudflare и репозиторию.
2. **R2 закрыт:** Cloudflare → R2 → `polski-go-audio` → Settings → *Public access*: **Disabled**, *r2.dev subdomain*: **Disabled**. Файлы озвучки отдаёт только Worker.
3. **Ночная резервная копия** (`.github/workflows/d1-backup.yml`):
   - GitHub → Settings → Environments → **production-backup** → секреты `CLOUDFLARE_API_TOKEN` (токен с правом *D1: Edit*, только на этот аккаунт), `CLOUDFLARE_ACCOUNT_ID`, `BACKUP_PASSPHRASE` (длинный пароль; сохраните его вне GitHub — без него копию не открыть);
   - расписание GitHub запускает **только из основной ветки**: задача заработает после слияния в `main`. До этого — ручная копия (раздел 3);
   - первый запуск — вручную: Actions → *D1 backup (nightly)* → *Run workflow*, затем учебное восстановление скачанной копии (раздел 4).
4. **Staging** (необязательно, но лучше до запуска): `docs/STAGING.md`, раздел 5 — база `polski-go-staging`, секреты, `npm run deploy:staging`.
5. **Дополнительное WAF-правило** (необязательно: ограничители в Worker уже есть): Security → WAF → Rate limiting rules → путь `/api/admin/login` — 10 запросов в минуту с IP, действие *Block* на 10 минут.
6. **Уведомления Cloudflare:** Notifications → Add → *Workers* (ошибки/превышения) на вашу почту — что доступно на бесплатном плане.

## 3. Резервные копии

- **Ночная копия** (после шага 2.3): каждую ночь в 02:17 UTC экспорт production-базы → gzip → шифрование AES-256 паролем → артефакт GitHub на 30 дней.
  Во время экспорта D1 не отвечает на запросы (секунды при нынешнем объёме) — поэтому ночью.
- **Ручная копия** на ваш компьютер: `npx wrangler login`, затем `npm run backup:d1` → `backups/polski-go-<дата>.sql` (папка не попадает в git). В копии — данные игроков: храните её как пароль.
- **Time Travel** (без копий): восстановление на любую минуту за последние 7 дней — раздел 5.

## 3а. Переезд базы в Европу и режим техработ (2026-11-23)

**Почему.** База D1 создалась сама при первой выкладке (в `wrangler.jsonc` не было ни id, ни региона) и оказалась в Океании: `/api/health` → `edge.d1.region = "OC"`, запрос к базе ~0,2 с. Smart Placement запускает Worker рядом с базой, поэтому каждый запрос игрока из Польши и Украины шёл в Австралию и обратно. Регион у существующей базы D1 поменять нельзя — нужна новая база в Европе и копирование.

**Что сделано в коде.** Режим техработ: секрет Worker `MAINTENANCE=on` — запись в базу запрещена (503 `maintenance`, в приложении «Идут технические работы — несколько минут»), webhook бота отвечает 503 (Telegram повторит сообщения позже), cron пропускается; чтение работает. Workflow **«D1 move to Europe»** (`.github/workflows/d1-move.yml`): включает техработы → создаёт новую базу (`eeur` — Восточная Европа или `weur`) → выгружает старую → переставляет выгрузку (`scripts/d1-import-order.mjs`: сначала таблицы, потом данные по связям, в конце индексы и триггеры — иначе загрузка падает на «no such table: main.users») → загружает → сверяет число строк каждой таблицы, индексы и триггеры (`scripts/d1-compare.mjs`). Сбой на любом шаге — техработы снимаются сами, приложение остаётся на старой базе. Workflow **«Maintenance»** — включить или выключить техработы вручную. Сухой прогон на локальной копии (миграции, контент, игроки): 72 таблицы, 7468 строк, 6 триггеров — совпадение полное; намеренно испорченная копия сверкой ловится.

**Доработки 2026-11-28 (версия 1.0, этап 1.1).**
- **База только на чтение в техработы** (`apps/server/src/db/read-only.ts`): запрет по методу запроса не ловил GET, которые пишут сами — `GET /api/quests` в техработы дописывал задания дня в `user_quests` (найдено тестом `maintenance.test.ts`). Такая строка после выгрузки пропала бы при переключении. Теперь любой INSERT/UPDATE/DELETE в техработы — 503 `maintenance`, база не меняется ни одним запросом.
- **Построчная сверка** (`scripts/d1-dump-diff.mjs`): после загрузки новая база выгружается ещё раз и сравнивается со старой по содержимому каждой строки, схеме, индексам и триггерам (порядок строк не важен). Значения в отчёт не попадают.
- **Найдена и исправлена ошибка перестановки**: `DELETE FROM sqlite_sequence` уезжал в конец выгрузки и обнулял счётчики AUTOINCREMENT в новой базе. Нашла построчная сверка на сухом прогоне.
- **Переключение одной командой** (`scripts/d1-switch.mjs <имя> <id>`): wrangler.jsonc (комментарии сохраняются), команды выкладки и копии в package.json, ночная копия; `--check` проверяет, что все места указывают на одну базу (тест `d1-move.test.ts` держит это и в репозитории).
- **Длинные строки по частям** (`splitLongInsert` в `scripts/lib/d1-sql.mjs`): D1 не принимает инструкции длиннее 100 КБ, а в production-базе есть строка `tts_cache` (аудио 86 КБ → инструкция 172 КБ). Загрузка в новую базу упала бы на ней — сухой прогон на тестовой базе этого не видел, нашла настоящая копия. Теперь такая строка вставляется с пустым значением и дописывается `UPDATE … || часть` (каждая < 90 КБ, байты те же; тест `d1-move.test.ts`).
- **Проверка на настоящих данных (2026-11-28, 05:15 UTC):** копия production-базы (128 игроков, 14 подписок, 15 платёжных событий, 43 МБ) → `d1-import-order` → чистая база → новая выгрузка → построчная сверка: **совпадает всё** — 68 таблиц с данными, 62 563 строки, 165 объектов схемы. Это первая настоящая копия базы; файл передан владельцу. `npm run restore:drill -- <копия>` теперь делает эту же построчную сверку.
- **Сухой прогон** `npm run restore:drill -- --self-test` теперь проходит и путь переезда: выгрузка → перестановка → пустая база → выгрузка → построчная сверка. Итог 2026-11-28: 75 таблиц, 15 таблиц с данными, 7452 строки, 165 объектов схемы — совпадение полное.
- **Замер одним способом до и после** (`scripts/d1-latency.mjs`, 30 запросов `/api/health`). Из этой среды: `NODE_USE_ENV_PROXY=1 NODE_EXTRA_CA_CERTS=/root/.ccr/ca-bundle.crt node scripts/d1-latency.mjs <адрес> 30`.

**Ночные резервные копии сейчас не делаются** (разовая копия 2026-11-28 сделана вручную, см. выше). Workflow «D1 backup (nightly)» каждую ночь завершается «успешно», но шаги выгрузки пропущены: в environment `production-backup` нет секретов (проверено по журналу запуска 2026-11-27: Export — skipped, артефактов копий нет ни одного). Единственная защита — Time Travel Cloudflare (7 дней). Те же секреты нужны для переезда — пункт 1–3 ниже закрывают обе задачи.

**Что сделать владельцу.**
1. **Токен Cloudflare:** dash.cloudflare.com → My Profile → API Tokens → Create Token → Custom token. Права: *Account → D1 → Edit* и *Account → Workers Scripts → Edit*; Account Resources — свой аккаунт. Скопировать токен.
2. **Account ID:** Cloudflare → Workers & Pages → справа «Account ID».
3. **GitHub:** репозиторий → Settings → Environments → создать `production-backup` → Add secret: `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `BACKUP_PASSPHRASE` (длинный пароль; хранить вне GitHub). Сразу после — Actions → «D1 backup (nightly)» → Run workflow: в итоге должен появиться артефакт `d1-backup-<дата>`; затем учебное восстановление этой копии (раздел 4).
4. **Разрешение на переезд** — написать разработчику «переезд разрешаю». Без этого production-базу не трогаем.
5. **Переезд** — в тихое время (ночью по Варшаве): Actions → «D1 move to Europe» → Run workflow → регион `eeur`, имя `polski-go-eu`, source пусто, confirm `ПЕРЕЕЗД`. 5–10 минут, приложение в это время только читает. В итоге запуска — id новой базы и готовая команда.
6. **Переключение** (разработчик): `node scripts/d1-switch.mjs polski-go-eu <id>` → `node scripts/d1-switch.mjs --check` → `npm test` → коммит и пуш → выкладка (~3 мин) → `/api/health`: `migration` прежняя, `edge.d1.region` = `EEUR`; замер `scripts/d1-latency.mjs` → строка «после» в таблице выше.
7. Actions → «Maintenance» → `off`. Приложение снова пишет — уже в новую базу.
8. Старую базу `polski-go` не удалять минимум 7 дней, потом удалить в Cloudflare → D1 (только после явного решения владельца).

**Откат.**
- *До шага 7 (техработы ещё включены):* в старую базу за время работ ничего не писалось — `node scripts/d1-switch.mjs polski-go <старый id>` (id: Cloudflare → D1 → polski-go) → пуш → выкладка → Maintenance off. Потерь нет.
- *После шага 7 (игроки уже писали в новую базу):* к старой базе возвращаться **нельзя** — в ней нет новых записей (прогресс, покупки, платежи). Откат — тем же workflow в обратную сторону: Maintenance on → «D1 move to Europe» с `source` = `polski-go-eu`, новым именем (например `polski-go-r1`) и нужным регионом → `d1-switch.mjs` на неё → выкладка → Maintenance off. Сверка та же, построчная.
- *Если сбой в самом workflow:* техработы снимаются сами, приложение остаётся на старой базе. Пустую новую базу можно удалить или использовать повторно (workflow проверяет, что она пустая).

## 4. Проверка восстановления (раз в месяц и после изменения схемы)

```bash
npm run restore:drill -- --self-test            # без Cloudflare: миграции + seed → экспорт → чистая база → сверка таблиц
BACKUP_PASSPHRASE=… npm run restore:drill -- polski-go-<дата>.sql.gz.gpg   # настоящая ночная копия
```

Скрипт заливает копию в **локальную** базу (Cloudflare не трогает), печатает число строк по таблицам игроков и прогресса и пишет файл
в правильном порядке (`.wrangler/restore-drill/restored.ordered.sql`).

**Важно (найдено учебным восстановлением 2026-11-04):** «сырой» экспорт `wrangler d1 export` в пустую базу **не заливается** —
таблицы в нём по алфавиту, и `exercises` со строками идёт раньше `lessons` (ошибка `no such table: main.lessons`). Скрипт переставляет:
сначала все таблицы, потом строки, потом индексы и триггеры. Для аварийного восстановления в новую базу используйте **только этот файл**.

## 5. Откат

**Сломалась выкладка (код), база в порядке** — откатить только код:
1. Cloudflare → Workers → polskie-go → Deployments → предыдущая версия → *Rollback* (или `npx wrangler rollback`). Статические файлы откатываются вместе с версией.
2. Проверить `/api/health` (коммит) и открыть приложение.
3. Исправить причину в ветке; следующий пуш выкладывает исправление.

**Испорчены данные (ошибочная миграция, массовая правка в админке)** — откатить код и базу:
1. Сначала код (как выше), иначе испорченная логика продолжит писать.
2. Найти закладку из журнала сборки этой выкладки (строка `bookmark` из `wrangler d1 time-travel info` в начале `deploy:cf`) или выбрать время.
3. `npx wrangler d1 time-travel restore polski-go --bookmark=<закладка>` (или `--timestamp=2026-11-04T10:00:00Z`).
4. **Всё, что игроки сделали после этой точки, пропадёт**, в том числе платежи Stars: сверить журнал платежей Telegram и при необходимости выдать Premium вручную (админка → пользователь → Premium).
5. Команда печатает закладку «до восстановления» — с ней можно вернуть базу обратно, если откат был лишним.

**База удалена или вне окна 7 дней** — создать новую базу, залить файл из раздела 4 (`npx wrangler d1 execute <новая база> --remote --file restored.ordered.sql`),
поменять `database_id` в `wrangler.jsonc`, выложить.

## 6. Мониторинг и разбор инцидента

1. **Админка → Обзор → «Ошибки за 24 часа»**: сервер / приложение / CSP, сообщение, путь, сколько раз, когда последний раз. Пусто — зелёное «нет».
2. **Workers Logs** (Cloudflare → Workers → polskie-go → Logs): полный стек серверных ошибок, ошибки cron (напоминания, очистка).
3. **`/api/health`**: какой коммит работает, применена ли последняя миграция, бот, сколько озвучки готово.
4. Сломался вход у многих сразу — проверить ограничители: ответ `429 rate_limited` на `/api/auth/telegram`. Лимит 60/мин на IP рассчитан на мобильный NAT;
   при массовом запуске его можно поднять в `wrangler.jsonc` (`RL_AUTH` → `limit`) и выложить.
5. После инцидента — запись в `docs/QA_RESULTS.md`: что случилось, как заметили, что исправили.
