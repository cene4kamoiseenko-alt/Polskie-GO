# Архитектурные решения POLSKI GO

Это журнал архитектурных решений (ADR) проекта. Каждая запись фиксирует одно решение: какая была задача, что выбрали, какие варианты отвергли, к чему это привело и чем решение проверено.

Как вести журнал:
- структура каждой записи одна и та же: Контекст, Решение, Альтернативы, Последствия, Проверка;
- новая запись получает следующий номер `ADR-NNN` и добавляется в конец журнала;
- существующие записи не переписываются задним числом: если решение меняется, пишется новая запись, которая ссылается на старую;
- в разделе «Проверка» указывается только то, что реально проверено. Пока прогона нет, так и пишется: «ожидает прогона e2e».

## ADR-001 — Шторка города: разделить drag и скролл

### Контекст

В шторке города `drag="y"` и прокручиваемое содержимое были на одном элементе. framer-motion по умолчанию ставит `touch-action: pan-x` на `drag="y"`, и этот жест перехватывал скролл.

### Решение

- `dragListener={false}`: перетаскивание запускается только из ручки через `useDragControls`. Хук экспортирует `apps/web/src/lib/motion.ts`.
- Прокручиваемое содержимое находится в `[data-sheet-scroll]` с `overflow-y-auto` и `[touch-action:pan-y]`.
- Футер с CTA вынесен за пределы скролла.
- Закрытие шторки: по ручке, по кнопке ✕ (`data-sheet-close`), по Escape и по системной кнопке BackButton Telegram.
- Высота `.sheet-panel` ограничена `90dvh` (`apps/web/src/index.css`).
- Закрытие перетаскиванием: смещение больше 90 px или скорость больше 600.

### Альтернативы

- Оставить drag на всём листе. Конфликт со скроллом при этом сохраняется.
- Использовать сторонний компонент шторки. Это новая зависимость, её не добавляем.

### Последствия

- Закрыть шторку можно только за ручку, по крестику, по Escape или системной кнопкой Back в Telegram.
- Скролл содержимого шторку не закрывает.

### Проверка

E2E-сценарий шторки на ширинах 360, 390 и 430 px (`scripts/browser-check.ts`) — ожидает прогона e2e.

## ADR-002 — Сегодня на главной: отдельные состояния вместо вечного скелетона

### Контекст

Скелетон показывался, пока список `daily` был пустым. Поэтому при офлайне или пустом дне он висел вечно.

### Решение

Блок «Сегодня» реализован компонентом `TodayTasks` (`apps/web/src/screens/Home.tsx`). Текущее состояние задаётся атрибутом `data-today`:

- `loading` — только пока запрос идёт (`isPending` и запрос не на паузе);
- `offline` — запрос на паузе без сети;
- `error` — ошибка с кнопкой «Повторить»;
- `empty` — сервер вернул ноль заданий;
- `active` — есть задания, которые ещё не выполнены;
- `done` — все задания выполнены, показывается строка «новые задания через N ч».

Скелетон показывается только на время загрузки. Вспомогательная функция `isOfflineError` находится в `apps/web/src/components/ui.tsx`.

### Альтернативы

- Оставить скелетон с таймаутом. Это скрывает проблему и не сообщает о ней пользователю.

### Последствия

- Пустой день показывает честное сообщение, а не пустую сетку.

### Проверка

E2E-сценарии состояний — ожидает прогона e2e.

## ADR-003 — Время в правиле старого экзамена Łódź (time-aware legacy)

### Контекст

Legacy-правило открывало экзамен города, если пройдены старые уроки. Новые уроки Łódź (`lodz-5`…`lodz-8`) добавлены позже. Пользователь, который прошёл старые уроки до расширения, не должен потерять доступ к экзамену, а новый пользователь должен пройти весь город.

### Решение

В `apps/server/src/services/journey.ts` значение `legacyDone` считается только по тем старым урокам, которые пройдены не позже момента добавления новых уроков (минимальный `createdAt` новых уроков). Новые уроки засеяны позже, поэтому при первом прохождении старых уроков новый пользователь проходит весь город.

### Альтернативы

- Фиксированный флаг в БД. Это требует миграции и данных.

### Последствия

- Правило зависит от `createdAt` уроков, поэтому при переносе уроков их `createdAt` трогать нельзя.

### Проверка

`apps/server/test/lodz-expansion.test.ts` — два теста. Они прошли при последнем прогоне серверных тестов.

## ADR-004 — Порядок работы и проверки

### Контекст

Проект ведётся небольшой командой; важно не терять работу и не ломать production, потому что любой пуш в рабочую ветку выкладывает приложение.

### Решение

- Правила работы с репозиторием, ветками и проверками — `CONTRIBUTING.md`.
- Тяжёлые прогоны (e2e, screens, a11y, perf) запускаются по одному, файлы во время e2e не меняются.
- Один файл — один редактор в момент работы.
- Перед коммитом заново запускаются typecheck и затронутые тесты; перед пушем — typecheck, `npm test` и content-lint.

### Последствия

- При изменении правил обновляется `CONTRIBUTING.md`.

## ADR-005 — Живописный слоистый Бобек и единый резолвер образа

Полный текст — `docs/ADR-005-PAINTERLY-BEAVER.md`. Кратко:

- Решение: живописная 2.5D «бумажная кукла» на общем холсте 1024 с якорями; голова и морда только из базы; одежда — слои; цельные костюмы — помеченный `legacy-whole-look` на переходный период; вещь без живописного слоя (`pending`) не рисуется и не продаётся за Złotki.
- Отклонено: плоский SVG-риг (решение владельца), комбинаторные спрайты, скелетные рантаймы, 3D.
- Ядро — `packages/shared/src/look` (`resolveLook`, `tryOn`, `equip`, `unequip`, `canPurchase`, DOM-контракт `data-look-*`). В web и server пока не подключено (этапы M1–M3 плана миграции).
- Проверка: тесты ядра в shared (148) и тест «manifest ↔ каталог» в `apps/server/test/look-catalog.test.ts` (4).

## ADR-006 — Правило времени для legacy-экзамена только в Łódź (пересмотр ADR-003)

### Контекст

ADR-003 сделал правило времени общим для всех городов из `LEGACY_CITY_LESSONS`. Для Варшавы и Кракова до этого действовало правило 3.x: старые уроки, пройденные в любой момент, открывают экзамен. Пользователи, прошедшие их после тогдашнего расширения, имели доступ и теряли его после обновления.

### Решение

Правило времени действует только для городов из `LEGACY_BEFORE_EXPANSION` (сейчас `lodz`). Варшава и Краков — снова правило 3.x. Код: `apps/server/src/content/legacy.ts`, `apps/server/src/services/journey.ts`.

### Альтернативы

- Миграция с флагом «доступ к экзамену заслужен» в БД: надёжнее при будущих расширениях, но требует миграции данных. Отложено до следующего расширения города.

### Последствия

- Новый пользователь Варшавы и Кракова по-прежнему открывает экзамен шестью/пятью старыми уроками (как в 3.x). Это осознанно: закрыть уже открытое нельзя.
- Следующее расширение города добавляется в `LEGACY_BEFORE_EXPANSION` одновременно с новыми уроками.

### Проверка

`apps/server/test/legacy-exam-access.test.ts` — 6 тестов, код 0. Тесты Варшавы и Кракова падают на логике ADR-003 (воспроизведено).

## ADR-007 — Магазин и гардероб на ядре образа (ADR-005, этап M3)

### Контекст

ADR-005 §12 требует: не списывать Złotki за вещь без живописного изображения (`pending`), а надевание вести по правилам слотов ядра (`equip()`), снимая конфликты в одном атомарном пакете. До M3 сервер знал только правило «один предмет на слот каталога» (`EXCLUSIVE` в `apps/server/src/services/shop.ts`):

- `buyItem` продавал любую вещь каталога, включая 23 `pending`;
- костюм и куртка или шапка одновременно оставались надетыми, хотя резолвер показывает только одно из них (`slot-conflict`).

В D1 нет интерактивных транзакций: чтение и пакет записи — разные вызовы.

### Решение

Код — `apps/server/src/services/shop.ts`.

- **Идентичность вещи для образа — `asset_key`.** Его клиент получает в `outfit.wear`, по нему резолвер рисует Бобека. В seed `asset_key` совпадает со slug.
- **`buyItem`.**
  - Порядок проверок: `item_not_found` (404), `reward_only` (400), `already_owned` (400), затем `canPurchase` ядра, `premium_required` (403), нехватка Złotki (400 из пакета).
  - Любой отказ `canPurchase` даёт `409 { error: 'visual_pending', message }`: `visual-pending`, а также `unknown-wearable` и `slot-mismatch` — одежда, которой нет в манифесте или у которой другой слот. Баланс, кошелёк, достижения и инвентарь не меняются: проверка стоит до `evaluateAchievements` и до пакета списания.
  - `visual_pending` проверяется раньше Premium: пользователя нельзя отправлять покупать Premium ради вещи, которую всё равно не продадут.
  - Награды (квест, город, достижение, миссия) идут через `grantItem` и seed, `buyItem` не используют — выдаются как раньше.
- **`listShop`** аддитивно отдаёт у каждой вещи `visualStatus`: `ready`, `legacy-whole-look`, `not-wearable` (домик), `pending` или `unknown`. Купить за Złotki можно только первые три. Остальные поля не менялись.
- **`equipItem`, надевание.**
  - Набор вытесняемого — `equip()` ядра над всем манифестом, то есть всё, что вообще конфликтует с вещью, плюс старое правило «тот же слот каталога». Старое правило убирает и вещи, которых нет в манифесте.
  - Снятие идёт условием `equipped = 1 AND item_id IN (… slot = ? OR asset_key IN json_each(?))` в том же пакете D1, что и надевание. Условие проверяется в момент записи, а не по прочитанному раньше снимку. Один JSON-параметр вместо `IN (?, ?, …)` — из-за лимита параметров запроса D1.
  - Для надетых вещей результат совпадает с `equip(current, item).equipment`, то есть с тем, что примерка (`tryOn`) показывает в `removed`.
- **`equipItem`, снятие** меняет только эту вещь, как `unequip()` ядра. Фирменное худи резолвер покажет сам (`default`), запись не нужна. Сам `unequip()` не вызывается: он не меняет другие вещи, поэтому вызов ничего бы не добавил к записи одной строки.
- **`pending`-вещи** во владении (купленные до M3 или наградные) надеваются. Из `user_inventory` ничего не удаляется. Формат `outfit` (`{ wear: { SLOT: assetKey }, house }`) не изменился. Миграций нет.

### Альтернативы

- **Снимок:** прочитать надетое, вызвать `equip(current)`, снять по списку id. Отклонено: гонка. Тест с параллельными «дракон + куртка + кепка» на такой реализации оставляет в БД все три вещи (воспроизведено мутацией кода). Условие внутри пакета эту гонку закрывает.
- **Миграция, чистящая старые конфликты.** Отклонено: это правка пользовательского состояния, а резолвер такие данные переживает. Конфликт в слоте исчезает при следующем надевании, которое этот слот затрагивает.
- **Код 400, как у `reward_only`.** Отклонено: `reward_only` — постоянное свойство вещи, а `visual_pending` — временное состояние до появления слоя. Отдельный код 409 позволяет клиенту показать «скоро».
- **Убрать `pending` из ответа `/shop`.** Отклонено: купленные и наградные `pending`-вещи должны оставаться в гардеробе.
- **Продавать одежду, которой нет в манифесте (`unknown`).** Отклонено правилом владельца: нет изображения — нет списания.

### Последствия

- **Поведение надевания изменилось** (вопрос 4 ADR-005):
  - костюм снимает вещи тех слотов, которые занимает. Художник снимает шапку, шарф, куртку и аксессуар; дракон — куртку и шапку;
  - куртка, шапка, шарф, обувь или аксессуар снимают костюм, который занимает их слот;
  - рюкзак, очки и рамку костюм не снимает. Повар совместим с `hat-chef`.
- **Порядок ошибок покупки изменился:** у своей Premium-вещи при истёкшем Premium теперь `already_owned`, а не `premium_required`. Клиент для своих вещей кнопку покупки не показывает.
- **До эталона за Złotki продаются** из одежды только `costume-artist`, `costume-winter`, `costume-dragon` и две рамки, плюс вещи домика. Это влияет на экономику Złotki (§16 промпта).
- **Новая одежда, заведённая в админке без записи в манифесте,** не продаётся (`visualStatus: 'unknown'`), пока её не добавят в `packages/shared/src/look/manifest.ts`. Выдать её наградой можно.
- **Клиент:**
  - текущий `Shop.tsx` показывает цену и кнопку покупки у `pending`-вещей, а для Premium-вещей без Premium — кнопку «только Premium»;
  - после M3 нажатие покупки даёт 409 `visual_pending` и тост с текстом сервера, деньги не списываются;
  - экрану нужно по `visualStatus` показывать «скоро» вместо цены и вместо кнопки Premium.
- **`outfit()` не тронут.** При двух надетых вещах одного слота в старых данных `wear` берёт одну из них, без фиксированного порядка. Это исправляется следующим надеванием в этот слот.

### Проверка

- `apps/server/test/shop-look.test.ts` — 13 тестов:
  - `visualStatus` и неизменные поля `/shop`;
  - 409 без изменения баланса, кошелька, достижений и инвентаря;
  - `reward_only` раньше `visual_pending`;
  - покупка костюма и рамки с одним списанием, повтор — `already_owned`;
  - купленные до M3 и наградные `pending` надеваются;
  - каждый из 8 костюмов на полном наборе вещей даёт то же, что `equip()` ядра, рюкзак остаётся;
  - правила §6 ADR-005;
  - согласование старых конфликтов;
  - снятие как `unequip()`;
  - чужая или несуществующая вещь — `not_owned`;
  - откат пакета при сбое надевания (тестовый триггер D1);
  - отсутствие конфликтов при параллельных надеваниях.
- `apps/server/test/game.test.ts` — два теста покупали `pending`-вещи (`cap-green`, `crown-gold`). Они переведены на `costume-winter`, `frame-gold` и `costume-dragon` (рамки убраны из игры 2026-11-14: проверка Premium теперь на `costume-dragon`).
- Мутационная проверка: без `canPurchase` и правил ядра падают 7 из 13 новых тестов. При раздельных пакетах падает тест атомарности. При «снимке» падает тест параллельных надеваний.
- `npm test` — код 0: shared 148 из 148, server 147 из 147 (23 файла).
- `npm run typecheck` — shared, server и admin — код 0. web — код 2: ошибки в `apps/web/src/dev/Gallery.tsx`, это незакоммиченная работа по M1, этим решением не затронута.
- e2e не запускался. На устройстве не проверено.

## ADR-008 — Единый Бобек: технология рендера, движение слоёв и прототип механики (2026-10-27)

### Контекст

Владелец попросил настоящую модель Бобека со сменной одеждой: куртка меняет только куртку, кепка держится на голове, очки на глазах, рюкзак за спиной, анимации idle, blink, wave, happy, thinking, celebrate работают с выбранной экипировкой, комплект сохраняется. Архитектура уже выбрана в ADR-005 (вариант B: живописная «бумажная кукла» на холсте 1024 с якорями), ядро и рендерер есть (`packages/shared/src/look`, `BeaverLook`), сервер хранит экипировку (ADR-007). Нет одного: живописных слоёв. `LOOK_MANIFEST.base.status = 'pending'`, ни одной вещи `ready`.

### Пересмотр технологий под Telegram Mini App

Оценки веса — по состоянию знаний, в этой сессии онлайн не перепроверялись.

| Подход | Рантайм | Что даёт сверх B | Риски в Telegram WebView |
|---|---|---|---|
| **B: стопка `<img>` + CSS-трансформации** | 0 КБ | — | нет: обычные картинки, анимация на композиторе |
| PixiJS (WebGL-холст) | сотни КБ | тысячи спрайтов, фильтры | WebGL-контекст, память, лишнее для 10–20 слоёв |
| Spine | рантайм + платная лицензия редактора | скелет, mesh deformation | лицензия; редактор и риг — отдельная работа |
| Rive | WASM-рантайм | машина состояний, меши | WASM в старых iOS WebView, растровая живопись в мешах не проверена |
| DragonBones | свой рантайм или через Pixi | скелет | проект не развивается |
| glTF + three.js | крупный рантайм + 3D-модель | настоящий 3D | нет 3D-модели; стилизация под живопись хуже; батарея |

### Решение

1. Остаёмся на B для первой версии. Деформация меша для одежды не нужна: верх — вариант торса на позу, жёсткие вещи стоят на якорях (ADR-005 §5). К скелетному рантайму вернуться, если понадобятся плавные позы, которые не рисуются вариантами.
2. **Движение слоёв** — поле `motion` у слоя (`packages/shared/src/look/types.ts`, `LOOK_MOTIONS`): `blink` (веки, видны мгновение каждые ~4,6 с) и `wave` (лапа и рукав выбранного верха поворачиваются вокруг `motionOrigin` — плеча). `resolveLook` переносит поле в `LookRenderLayer`, `BeaverLook` ставит класс `look-motion-*`, ключевые кадры — в `index.css`. Движется только «живой» Бобек (`.is-live`: виден, от 96 px, один на экране), без «Меньше анимаций» и `prefers-reduced-motion`. Позы (idle, happy, thinking, celebrate) — разные позы базы по `moods`, как раньше.
3. **Запасной путь** не меняется. Пока база `pending`, приложение рисует цельные живописные позы `legacy-base` и цельные костюмы. Вещь без слоя не рисуется и не продаётся. При «Меньше анимаций» поза и одежда те же, движения нет.

### Прототип механики (не финальная графика)

- Страница `/__look-prototype` (`apps/web/src/dev/LookPrototype.tsx`) — отдельный lazy-чанк, в приложении не используется. Там шаги: 1 худи → 2 синяя куртка → 3 кепка → 4 очки → 5 змах → 6 перезапуск.
- Манифест — `apps/web/src/dev/lookPrototypeManifest.ts`. Те же `resolveLook`, `equip`, `BeaverLook`.
- Слои строит `scripts/look-prototype.mjs` из существующих поз `beaver/*.webp`:
  - мех, худи и рюкзак разделены по цвету; сложенные, они дают исходную позу пиксель в пиксель;

## ADR-009 — Отклик: один пакет D1 на запрос и Smart Placement (2026-10-28)

### Контекст

Владелец: «отклик очень долгий». Worker без placement работает рядом с пользователем, а D1 — в одном регионе, поэтому каждое последовательное обращение к базе стоит полный сетевой круг. Замер (`app.request` с подсчётом вызовов D1): ответ в уроке — 3 последовательных обращения, старт урока — 6, завершение — 8, `/api/quests` — 6, `/api/me` — 3. Бандл Worker — 2886 КБ (весь словарь ради одного списка тем).

### Решение

1. **Независимые чтения — одним `db.batch`.** Помощники `ctxReads`, `questReads`, `journeyReads`, `storyReads`, `answerReads` возвращают запросы, которые вызывающий код кладёт в общий пакет; `ctxFrom`, `questState(ctx, pre)`, `journeyFrom` собирают результат без новых обращений.
2. **«Сегодня» до того, как известен пояс.** День пользователя зависит от пояса из того же пакета, поэтому строки «за сегодня» (квесты дня и недели, дневная активность, лимит ИИ, скриня дня, подарок месяца) читаются по всем ключам, которыми «сегодня» может быть в любом поясе (UTC−12…UTC+14: три дня и их недели — `dayCandidates`, `periodCandidates`), и отбираются после.
3. **Ответ в уроке**: навык и расписание повторений читаются по ключу задания (ключ урока — id упражнения, слова — `w:<id>`); если задание сессии не совпало с догадкой, — отдельное чтение (`prefetched`).
4. **Завершение**: урок сессии — подзапросом по id сессии, нагороды достижений и снимок для повторного запроса — одним пакетом.
5. **Smart Placement** (`placement.mode = smart` в обоих wrangler-конфигах): Worker с несколькими обращениями к D1 работает рядом с базой; статические файлы по-прежнему отдаются из ближайшего дата-центра. Проверка после выкладки — `/api/health` → `edge` (колония Worker, время обмена с D1, регион D1).
6. **`minify`** и `content/topics.ts`: бандл 2886 → 1460 КБ (gzip 553 → 337 КБ); минифицированная сборка проверена в Miniflare.

Итог по последовательным обращениям: ответ 3 → 2, старт урока 6 → 2, завершение 8 → 5, квесты 6 → 1 (3 при первом заходе за день), `/api/me` 3 → 1, достижения 3 → 2.

### Последствия

- В пакет `db.batch` нельзя класть JOIN (Drizzle путает одноимённые колонки) — такие запросы идут параллельно через `Promise.all`.
- Smart Placement включается не сразу и только при достаточном трафике; без него выигрыш даёт п. 1–4.

## ADR-010 — Premium: только то, что работает, и правила Telegram Stars (2026-10-28)

### Контекст

Premium обещал ИИ-преподавателя (без ключа не работает), «подготовку к государственному экзамену» (её нет) и «аналитику ошибок»; по факту давал лишь эксклюзивные вещи. Нет `/paysupport` и `/terms`, возврат по старому продлению не находился, недействительный платёж оставлял человека без звёзд и без Premium.

### Решение

- Состав Premium: щит серии (один пропуск в неделю, `updateStreak(..., { shield })`, колонка `streak_shield_day`, миграция 0013), сцены Premium (аренда, первый рабочий день, запись к врачу — бывшие «скоро»), ×2 дневной лимит XP тренировок, подарок месяца (150 Złotki + вещь Premium, ключ `premium-gift:<user>:<YYYY-MM>`), корона в рейтинге, эксклюзивные вещи. ИИ — только когда он подключён (`/api/me` → `ai.configured`).
- Оплата: Premium включается только по `successful_payment`; недействительный платёж — автоматический `refundStarPayment`; `handleRefund` идемпотентен и снимает Premium по подписке, оплаченной этим платежом; возврат из админки (SUPERADMIN). `/terms`, `/paysupport` (обращение → админка → ответ в бот, таблица `support_requests`).
- Скасование: Premium действует до конца оплаченного периода (правило Telegram); после — выключен проверкой `expires_at`.

### Последствия

- Отмену подписки в самом Telegram бот не видит (у Bot API нет такого события): экран честно пишет, что продление идёт, пока подписка не отменена в Telegram, а по окончании периода Premium выключается сам.
- Возврат старого продления подписки Stars только записывается в журнал: подписка хранит charge id последнего платежа.

## ADR-011 — Пропуск месяца: сезонные локации с эксклюзивными миссиями (2026-10-31)

### Контекст

Владелец: «поменять условия Premium… ежемесячный пропуск с локациями — Рождественский пропуск, поездка в Energylandię, что-то локальное о Польше». Premium давал щит серии, три сцены, ×2 XP тренировок, подарок месяца и вещи — без регулярного нового контента.

### Решение

- **Сезон** — `content/seasons.ts`: даты (YYYY-MM-DD, включительно, по поясу ученика), город, сцена, цвет, 3 миссии и достижение-награда. Миссии сезона — обычные `Mission` с `season` и `category: 'season'`; они в `MISSIONS` (достижения, озвучка, seed и проверки контента видят их), но в общий список `/missions` не попадают — только в `pass`.
- **Доступ** (`seasonAccess` в `services/missions.ts`, проверяет сервер при старте): будущий сезон — закрыт для всех (`season_not_started`); текущий — первая миссия всем, остальные с Premium; прошедший (архив) — только Premium (`premium_required`).
- **Награда сезона** — достижение `MISSIONS_TAG:season-<slug>` (порог = число миссий, 150 Złotki и значок). Новой таблицы и миграции нет: прогресс сезона — это пройденные миссии в `user_missions`. Вещей-наград нет, пока для них нет живописных слоёв (ADR-005).
- **Без шагов «послушай»** в сезонных миссиях: озвучку генерирует только админка, а без аудио такой шаг не пройти. Реплики попадают в каталог озвучки сами (`audio-catalog.ts`).
- **Сезоны на старте:** «Ноябрь в Познани» (2026-11-01…30: rogale świętomarcińskie, 11 ноября, andrzejki), «Польское Рождество» (2026-12-01…31: ярмарка в Кракове, Wigilia, Sylwester), «Поездка в Energylandię» (2027-07-01…31: билеты, очередь на горки, потерянный телефон).
- **Premium:** цены и тарифы не менялись. Пропуск месяца — первое, что даёт Premium (экран Premium, `/terms`, описание счёта Stars).

### Последствия

- Январь–июнь 2027 без сезонов: календарь покажет следующий — Energylandia. Чтобы пропуск был каждый месяц, сезоны нужно добавлять до их начала. Предложенные темы: январь–февраль — ferie в Закопане (Krupówki, oscypek, лыжи); февраль — Tłusty Czwartek (pączki); март–апрель — Wielkanoc и śmigus-dyngus; май — majówka на Мазурах; июнь — Wianki в Кракове; август — Jarmark Dominikański в Гданьске; сентябрь — grzybobranie.
- Новый сезон = записи в `SEASONS`, миссии в `seasons.ts`, достижение в `ACHIEVEMENTS`, слова в `vocab-seasons.ts`; тест `pass.test.ts` проверяет пересечения дат, теги, достижение и отсутствие шагов «послушай».
- Отдельная покупка пропуска за Stars (без Premium) не сделана: это новая цена — решение владельца.

## ADR-012 — Иллюстрированная карта: живописная картинка и настоящие кнопки поверх (2026-10-31)

### Контекст

Владелец прислал пакет POLSKI_GO_MAP_ASSETS: утверждённую 2.5D-карту Польши (`map_full.png`, 941×1068) с уже нарисованными табличками городов, звёздами и Бобеком у Кракова, точки 20 городов и демо с pan/zoom. Задание: заменить визуал карты, сохранив функции; прогресс и доступ — только с сервера; не дублировать нарисованные подписи; карту можно откатить отдельно.

### Решение

- **Данные** — `packages/shared/src/mapArt.ts`: `MAP_ART` (размер, пометка «подписи впечены», зона впечённого Бобека) и `MAP_SPOTS` — рамки табличек, измеренные по самой картинке. Ключ — slug города приложения; алиасы id пакета (`gorzow_wielkopolski`, `zielona_gora`) — `MAP_PACK_ALIASES`. **Sopot** нарисован, но этапа нет (убран из маршрута, `REMOVED_CITIES`): `city: null`, карточка объясняет и ведёт к Gdańsk. **Zakopane** (финал маршрута) на картинке нет — приложение рисует свою кремовую табличку и круглый медальон с видом Татр (кадр из панорамы города, 256 px — на малом размере временный кадр не мутный) в горах к юго-западу от Кракова; тот же вид — в карточке города.
- **Компонент** — `components/IllustratedMap.tsx`: одна «сцена» с transform (translate + scale), внутри картинка, прозрачные зоны нарисованных зданий (`models`, нажатие пальцем) и прозрачные `<button>` по `mapHitRect` (табличка — одна кнопка города для клавиатуры) — после перетаскивания и масштаба зона всегда совпадает с табличкой. Жесты на Pointer Events: перетаскивание с инерцией, щипок двумя пальцами вокруг середины, колесо/трекпад вокруг курсора, кнопки + / − / «к моему городу», клавиатура (стрелки, + / −, 0, Tab по городам в порядке маршрута). Карта всегда закрывает ширину экрана и окно между шапкой и карточкой; `touch-action: none` и `data-no-swipe` — жест карты не перелистывает вкладки.
- **Поверх картинки — только новое**: значок «замок» / «галочка» (из `journey`), кольцо и булавка «ты здесь», свечение выбранного города, маркер поездки после экзамена. Нарисованные подписи и звёзды не дублируются.
- **Экран** — `screens/Map.tsx`: карта на весь экран, сверху настоящие серия / Złotki / Premium и «Твоё путешествие N/20», снизу компактная карточка выбранного города (статус, уроки, прогресс, «Продолжить» → первый `available` урок с сервера; Premium-урок без подписки → `/premium`). «Подробнее» открывает прежнюю шторку с темами, сундуками и требованиями доступа. Сервер остаётся единственным источником прав: урок закрытого города он не начнёт (`403 lesson_locked`).
- **Загрузка и края**: WebP q76 (205 КБ) с явными размерами; размытая копия 24 px (data URI) — только пока файл грузится. Сверху карта не опускается ниже края экрана (шапка с серией и Złotki лежит поверх, без второго отступа под Telegram и без подложки), снизу её край поднимается лишь до карточки и уходит в облачную дымку — «мыльных» полос нет (замечание владельца 2026-10-31). Сдвига раскладки нет.
- **Знакомство** показывает ту же картинку (`MapPreview`) с кольцом на стартовом городе. Старая SVG-карта (`PolandMap.tsx`) удалена.

### Последствия

- Бобек на карте впечён у Кракова и не носит образ из гардероба; для новичка (старт — Warszawa) он стоит не в его городе, «ты здесь» показывает булавка. Финальный шаг — чистый фон без табличек, звёзд и Бобека (промпт — `docs/MAP_V17.md`): тогда `MAP_ART.baked = false`, и по тем же рамкам рисуются настоящие таблички, звёзды по прогрессу и Бобек в образе.
- Откат только карты: `git revert` коммита «Illustrated map…» — уроки, награды, сервер и API не менялись.
- Проверки: `apps/server/test/map-art.test.ts` (рамки, пересечения, точки пакета, все города маршрута), `scripts/map-screens.ts` (жесты, совпадение кнопок после pan/zoom/pinch, закрытые города, урок, клавиатура, сеть, тема, ориентация), A4 в `scripts/browser-check.ts`.

## ADR-013 — Готовые образы Бобека вместо слоёв (2026-11-01)

### Контекст

ADR-005 строил единую живописную модель: база + слои одежды на общем холсте 1024, этапы M4 (`etalon-1`, 18 частей) и M5 (`etalon-2`, 8 частей). Слоёв за всё время не появилось (0 `ready`), а владелец прислал 31 готовую картинку Бобека: все 16 сочетаний (худи + кепка / очки / шарф / рюкзак) в позе «машет с картой», 8 сочетаний в позе «руки разведены» и 7 костюмов (совпадают с уже подключёнными). Решение владельца: единую модель не делать, под все стили и смены одежды подставлять готовые картинки, в магазине предметов.

### Решение

- Новый статус предмета `prerendered` (`LOOK_VISUAL_STATUSES`): для предмета есть готовые образы. Продаётся и надевается, как `ready` и `legacy-whole-look`.
- Таблица `LOOK_VARIANTS` (`packages/shared/src/look/variants.ts`): набор вещей → картинка по позе (`wave`, `open`). Худи — в `includes` (есть на каждой картинке), вещи-оси — кепка, очки, шарф, рюкзак.
- Новый режим `variant` у `resolveLook`: точный набор вещей → его картинка; нет точного → наибольший вмещающийся образ + причина `no-variant`. Только фронтальный вид.
- Стартовый набор (худи + рюкзак) остаётся цельным `legacy-base` с 14 позами владельца (решение владельца 2026-11-01). Костюмы — `legacy-costume`, закрывают готовые образы.
- Конвейер `scripts/build-bobek-variants.mjs`: вырезка фона серии 24–31, очистка разводов серии 01–16, общий холст с масштабом и линией ног позы `wave`; мастера — `docs/design/v18/bobek31/`.
- Интерфейсы не менялись: `BeaverLook`, `Beaver`, `equip`, `tryOn`, `POST /api/inventory/equip`, `GET /api/shop` (кроме нового значения `visualStatus`). Слои `layered` остаются в резолвере и тестах на синтетическом манифесте, но шаговая модель не планируется.

### Последствия

- Одетый Бобек имеет две позы вместо 14; у стартового набора позы прежние. Следующая часть образов (новые вещи или позы) = файлы + строки таблицы; полная сетка растёт как 2^N, поэтому для новых вещей нужен либо полный набор картинок, либо принятие частичной сетки (`no-variant`).
- Известные дефекты мастеров серии 09–16 (призраки внутри силуэта) требуют ретуши владельца: `docs/BOBEK_VARIANTS.md`.
- Кепка, круглые очки и шарф теперь продаются; цены прежние (40 / 50 / 60 Złotki) — решение владельца, оставлять ли их в магазине.
- **Вторая партия (2026-11-01):** джинсовая куртка и дождевик — `prerendered`, 4 образа с рюкзаком (часть сетки не нарисована). Правило частичной сетки: образ с наибольшим числом вмещающихся вещей, при равенстве — важнее вещь по `LOOK_VARIANTS.priority`; остальное `no-variant` («Для этого сочетания нет картинки» в примерочной). Образы с вещами вне каталога (чёрная куртка + наушники, пуховик + шапка + шарф, пальто + тёплые наушники) стали шестью **скинами** — цельными предметами `COSTUME` по 400 Złotki, `legendary`, без наград и Premium («дорогие, как цельные скины», владелец 2026-11-01): занимают всю одежду кроме рюкзака, картинки — `costumes/<имя>` (512, @256, @512, @1024). Цена и названия — мои стартовые значения, правятся в админке.
- **Третья партия (2026-11-01):** 5 картинок на светлом фоне (кепка с PL): перерисованы сочетания 14, 16 (серия 01–16, были с разводами), «джинсовая + кепка + очки + рюкзак» (кепка теперь с PL) и «дождевик + очки + рюкзак»; новое сочетание «дождевик + кепка + очки + рюкзак». Конвейер ставит такие картинки по рамке образа-аналога, а не по общему для серии преобразованию.
- **Четвёртая партия (2026-11-01):** 14 картинок с куртками без худи и красной вязаной шапкой. Куртка и худи — один слот `top` и вместе не надеваются, поэтому образы четвёртой партии нарисованы **без худи**; образ без худи заменяет образ того же набора вещей с худи под курткой (ключ замены в конвейере — набор без худи), а четыре сочетания, для которых образа без худи нет, остались с худи под курткой (имя файла с префиксом `hoodie-`). `LOOK_VARIANTS` — 32 образа. Новый предмет `beanie-red` (`HAT`, `prerendered`, слот кепки; 60 Złotki, `common` — мои стартовые значения): образы с шапкой есть только с куртками. Приоритет вещей при частичной сетке: куртка, кепка, шапка, очки, шарф, рюкзак. Код резолвера не менялся: `includes` задаёт слот `top` как «подкладку», куртка его перекрывает. Конвейер: серия `bare` с выравниванием линии ног (`snapBottom`).

## ADR-014 — Экран загрузки по слоям владельца (2026-11-01)

### Контекст

Владелец прислал два архива: четыре цельных концепта экрана загрузки (941×1672) и те же концепты, автоматически разделённые на слои (фон, логотип, Бобек) с
HTML-прототипом. Прежняя заставка — панорама Варшавы и растровая поза Бобека — заменяется ими.

### Решение

- Заставка (`components/Splash.tsx`) — сцена 941×1672 внутри экрана как `cover`: фон, логотип и Бобек лежат по процентам кадра (`lib/splashArt.ts`), поэтому не расходятся на
  любых экранах; поверх — стеклянная карточка. Карточка остаётся живым HTML с **реальным** прогрессом из `lib/boot.ts` (вход → профиль → первый экран), без таймеров и
  фальшивых запросов; ошибка, нет сети и медленный этап сохраняют прежние селекторы (`.splash-card`, `data-boot`, `data-boot-error`).
- Мгновенная заставка в `index.html` показывает тот же фон и логотип на тех же пикселях (CSS без JS); логотип появляется один раз, React его подхватывает.
- Рабочая тема одна — `royal`. `sunset` и `adventure` — только для разработки (`?splash=`), лежат в `src/dev/splash-themes` и вырезаны из сборки плагином Vite;
  тема `soft` («Мягкий») не берётся по решению владельца (Бобек размыт: резкость 476 против 714–935).
- «Чистые» фоны архива не чистые (призраки логотипа, Бобека и карточки): `scripts/build-splash-art.mjs` перерисовывает эти три зоны, оригиналы остаются в
  `docs/design/v19/loading/`. Это промежуточное решение до чистых мастеров.
- Знакомство (первый шаг) использует ту же сцену, приподнятую на 5,5 % (`lift`), и компактную реплику на малых экранах.
- **Логотип с украшением — отдельная группа** (замечание владельца: логотип был слишком крупным и под кнопками Telegram): украшение вынимается из оригинала слоем `orn.webp`, группа масштабируется по ширине экрана (≈ 74 %) и стоит под шапкой Telegram. **Минимальное время показа** 1700 мс (`SPLASH_MIN_MS`, решение владельца: заставку не успевали увидеть); бюджет повторного открытия в перфе 2200 мс. Dev-темы sunset / adventure убраны.
- **Слой Бобека чинится в конвейере** (владелец на телефоне увидел «лапы»): вырезка архива обрезала лапы и оставила просвечивающие полосы; пальцы достраиваются из оригинала (+46 px слоя вниз),
  внутри силуэта слой непрозрачен, покачивание ограничено (≤ 5 px, наклон ≤ 0,5°). Перерисовка фона вокруг Бобека сведена к кайме 2 px и полосе 10 px под самим слоем: широкая заливка размазывала фонарный столб.

- **Чистые мастера владельца (вторая версия, 2026-11-01).** Владелец прислал чистый фон (1536×1024, без логотипа, Бобека и карточки), Бобека и логотип с чистой альфой. Вся чистка призраков удалена из конвейера
  (`scripts/build-splash-art.mjs`: достройка лап, перерисовка зон вокруг Бобека, карточки, логотипа). Фон портретный собирается из альбомного мастера (масштаб 0,84, колонна за Бобеком, небо и брусчатка достроены программно),
  Бобек и логотип обрезаются по содержимому, альфа 253 → 255 и цвет кромки чинятся в `scripts/lib/sprite.mjs`. Украшение над логотипом остаётся слоем из концепта. Геометрия слоёв и числа `index.html` печатает конвейер.
- **Минимум показа заставки 2,4 с** (`SPLASH_MIN_MS`, было 1700: владелец попросил «ещё немного дольше»); бюджет повторного открытия в perf — 3000 мс.

### Последствия

- Заставка и первый шаг знакомства выглядят одинаково, сцена не прыгает при переходе. Бобек на заставке — слой владельца, а не поза из `assets/beaver`.
- Старая панорама (`warszawa-portrait-*`) удалена; откат — `git revert`.
- Не проверено на реальных iPhone / Android, в полноэкранном режиме Telegram, со скринридерами и на слабых устройствах.
- Подробности и ограничения — `docs/LOADING_SCREEN.md`.

## ADR-016 — Android: оболочка TWA и вход вне Telegram (2026-11-07)

### Контекст

Приложение — Telegram Mini App; владелец хочет выпустить его и в Google Play, чтобы оно одинаково работало в Telegram и в Android. Вход сейчас только по подписанным `initData` Telegram, оплата — Telegram Stars.

### Решение

- **Оболочка — Trusted Web Activity** (Bubblewrap, `android/twa-manifest.json`): тот же сайт и тот же код, без отдельной кодовой базы. Capacitor рассмотрен и отложен: нужен, если понадобятся нативные плагины (Billing, push); сейчас Digital Goods API в TWA покрывает оплату.
- **Платформа** определяется на клиенте (`lib/platform.ts`): Telegram / Android (`?source=twa`) / веб. Вне Telegram и не на localhost работает вход по ключу устройства.
- **Аккаунты без Telegram** — «гости» с отрицательным `users.telegram_id` (ограничения таблицы не меняются; настоящие id Telegram положительные), ключ устройства (256 бит, в базе только sha-256) и **одноразовый код переноса** (10 минут): так прогресс и покупки общие у Telegram и Android, а чужой Telegram id аккаунту не присваивается. Telegram Login Widget отложен: нужен домен в BotFather.
- **Платежи:** Stars — только в Telegram (`409 stars_unavailable` для гостя, интерфейс скрыт). Покупки в Android — Google Play Billing, отдельный этап; до него Premium в Android не продаётся (требование Google, иначе блокировка приложения).
- **Юридические страницы** отдаёт Worker (`/privacy`, `/delete-account`), связь с приложением — `assetlinks.json` из переменных Cloudflare.
- **Service worker** — только вне Telegram: офлайн-страница и кеш файлов сборки; данные игрока не кешируются.

### Альтернативы

- Нативное приложение или Flutter: отдельная кодовая база, месяцы работы.
- Вход через Google Sign-In / e-mail: нужны внешние сервисы и настройка владельцем; гость + код не требует ничего и работает сразу.
- Nullable `telegram_id`: требует перестройки таблицы `users` в D1 (рискованная миграция).

### Последствия

- Любой код, шлющий что-то по `users.telegram_id` (бот, напоминания, рассылки), обязан пропускать `telegram_id <= 0` — сделано в `jobs.ts`, проверяется тестом.
- Новые переменные Cloudflare: `STANDALONE_AUTH=on` (**по умолчанию вход вне Telegram выключен**: открытое создание аккаунтов исчерпало бы лимит записей бесплатной D1), `GUEST_DAILY_LIMIT`, `ANDROID_PACKAGE_NAME`, `ANDROID_SHA256_FINGERPRINTS`, `SUPPORT_CONTACT`.
- Не проверено на настоящем Android: сборка AAB, подпись, микрофон в оболочке, `assetlinks.json` с настоящим отпечатком.

### Проверка

`apps/server/test/standalone.test.ts` (18), `scripts/standalone-check.ts` (браузер, включая service worker на сборке), `docs/ANDROID_RU.md`.
